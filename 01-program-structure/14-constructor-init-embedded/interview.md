# Interview Questions: Constructor Initialization

## 1. What is the Static Initialization Order Fiasco?
**Answer:** It is a classic C++ bug where two global (or static) objects depend on each other, but because they are in different translation units (`.cpp` files), the compiler provides no guarantee about which object is constructed first. If Object A relies on Object B in its constructor, but Object A happens to be constructed first, the program will crash or exhibit undefined behavior.

## 2. How do you solve the Static Initialization Order Fiasco in C++?
**Answer:** The most robust solution is to use "Construct on First Use" (Meyer's Singleton). Instead of a global object, you wrap the object inside a function as a local `static` variable. C++ guarantees that local static variables are initialized the very first time control flow passes through their declaration.

## 3. When are global C++ constructors called in an embedded system?
**Answer:** They are called *before* `main()`. The startup assembly code (often `Reset_Handler`) calls a function like `__libc_init_array()`, which iterates through a table of function pointers generated by the compiler (the `.init_array` section), executing the constructor for every global object.

## 4. What is the benefit of `constexpr` constructors in embedded systems?
**Answer:** A `constexpr` constructor allows an object to be fully evaluated and initialized at **compile time**. The object is stored directly in Flash (or copied cleanly to RAM) with its final values already computed. It completely eliminates the need for runtime constructor code in `.init_array`, avoiding the Initialization Order Fiasco entirely and reducing boot time and Flash footprint.
