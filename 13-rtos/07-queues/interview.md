# Interview Questions: Queues

## 1. How does FreeRTOS prevent a task from wasting CPU cycles while waiting for data to arrive in an empty Queue?
**Answer:** When a task calls `xQueueReceive(queue, data, portMAX_DELAY)`, it makes an API call into the RTOS Kernel. The Kernel checks the queue buffer. If it is empty, the Kernel physically moves the Task's Task Control Block (TCB) out of the Ready List and into the Blocked List. Because the task is now Blocked, the RTOS Scheduler completely ignores it during SysTick evaluations. The task consumes exactly 0.00% of CPU time. The precise nanosecond another task (or an ISR) pushes data into the queue via `xQueueSend()`, the RTOS Kernel intercepts the push, instantly moves the waiting task back to the Ready List, and triggers a Preemptive Context Switch so the task can process the data immediately.

## 2. In FreeRTOS, Queues pass data by "Copy" rather than by "Reference". What is the primary architectural advantage of this design?
**Answer:** Pass-by-Copy fundamentally eliminates Race Conditions and complex memory management. If a Producer task creates a local `struct` on its stack and pushes it to a queue, FreeRTOS performs a `memcpy` of the struct's bytes into the Queue's isolated memory buffer. The Producer can immediately modify, overwrite, or delete its local struct without affecting the Consumer task, because the Consumer will read the secure, isolated copy from the Queue. If data were passed by Reference (pointers), developers would have to implement complex Mutex locks or dynamic allocation (`malloc`/`free`) to ensure the Producer didn't overwrite the memory while the Consumer was still reading it.

## 3. What happens if an Interrupt Service Routine (ISR) tries to push data to a Queue that is completely full?
**Answer:** In a standard Task, calling `xQueueSend()` on a full queue with a timeout allows the RTOS to put the Task to sleep until space frees up. However, an ISR is a hardware interrupt; it physically cannot be put to sleep (Blocked). Therefore, if an ISR calls `xQueueSendFromISR()` and the queue is full, the function will instantly return a failure code (e.g., `errQUEUE_FULL`). The RTOS will simply discard the data. The developer must write error-handling logic inside the ISR to track dropped packets, and critically, must re-architect the system (either increase queue depth or raise the Consumer task's priority) to ensure the queue never fills up in production.
