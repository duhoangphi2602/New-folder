# Interview Questions: Mutexes

## 1. What is a "Critical Section" and why must it be protected by a Mutex in a preemptive RTOS?
**Answer:** A Critical Section is any block of code that reads, writes, or modifies a shared resource (like a global variable, an array, or a hardware peripheral like I2C/UART) that is accessed by multiple tasks. In a preemptive RTOS, the Scheduler can violently pause a task at any exact nanosecond. If Task A is halfway through writing an I2C command and is preempted by Task B, which then sends its own I2C command, the hardware will receive a corrupted, interleaved command and crash. A Mutex acts as a physical lock; once Task A claims the Mutex, the RTOS guarantees that if Task B wakes up and tries to access the I2C, Task B will be forced to sleep until Task A finishes and returns the lock.

## 2. Why is attempting to use a global boolean flag (e.g., `bool is_busy = true;`) instead of an RTOS Mutex dangerous?
**Answer:** A boolean flag causes a devastating issue called Priority Inversion/Deadlock through CPU Starvation. If a task checks `while(is_busy) {}`, it creates a blocking loop in software, not in the RTOS Kernel. The RTOS sees the task is executing a `while` loop, assumes it is doing productive math, and gives it the CPU. If this is a high-priority task, it will consume 100% of the CPU waiting for the flag to become false. However, the low-priority task that currently holds the flag (and is supposed to set it to false) will never get CPU time to finish its job because the high-priority task is hogging the CPU. A Mutex solves this by telling the RTOS Kernel to physically put the waiting task into the Blocked List (0% CPU time) until the resource is free.

## 3. What happens if a task takes a Mutex, but a software error causes the task to skip the `xSemaphoreGive()` function?
**Answer:** This results in a permanent system Deadlock. The Mutex is essentially "lost". Because the task never gave the key back to the RTOS, the RTOS marks the resource as permanently locked. Any other task in the entire system that subsequently attempts to call `xSemaphoreTake()` on that Mutex will be placed into the Blocked List forever. The system will progressively freeze as more and more tasks queue up waiting for a key that will never be returned.
